# ORPHEUS development workflow

- Target build is Overwatch 1.74.0.0.104319. Finish the Soldier: 76 and Practice Range acceptance group first, then reuse the same checks for the next hero or map. Prefer evidence from the target build and small changes to shared mechanisms.
- Unattended tasks work on server code, data tools, tests, and documentation. Leave game startup, game controls, and client acceptance to the user unless the user explicitly authorizes a separate session.
- Keep each completed change focused. Inspect the working tree, run the relevant tests and checks, and review the staged diff. Update `CHANGELOG.md` in the same commit with the change, test results, client acceptance, and remaining issues. Use an English Conventional Commit such as `fix: retire obsolete body respawn timers` and add the trailer `Assisted-by: Codex` for Codex-assisted commits.
- Use the maintainer `leafall903` as the author of new ORPHEUS commits, with the verified GitHub noreply identity in the repository-local Git configuration. Check the effective author before committing and retain previous authorship in published history.
- Keep the active development branch `main`. The intended publication destination is `https://github.com/leafall903/ORPHEUS.git` on `main`. The inherited server remote is `upstream`. Preserve the original local history and publish from a separate, reviewed server tree. Make the GitHub repository public for the first validated upload.
- Before the first push, audit **every Git object reachable from the branch**, including historical files and commit metadata. Before later pushes, audit all outgoing commits and objects. Leave credentials, logs, captures, profiles, generated binaries, local caches, and unapproved third-party game assets or data off GitHub. A pattern in `.gitignore` affects untracked files only.
- Keep client research material and prepared runtime inputs in separate local storage. Validate that the publication checkout boots and serves the target scene with authorized external runtime data and no game installation or launcher DLL. Keep the existing upstream license notices and credits. The ORPHEUS contributor list is maintained separately in `CONTRIBUTORS.md`.
- After a tested commit and a successful publication audit, bring the reviewed change into the publication `main` and push normally. If authentication, the audit, branch protection or a non-fast-forward blocks the push, preserve the local commit, record the cause and continue local development. Avoid force pushes, remote deletion, history overwrites, automatic releases, and automatic version bumps.
- On the current development machine, run `python -B work/sync_orpheus_publication.py --commit <tested-development-sha> --runtime <prepared-runtime-directory>` from the workspace root after committing. This exports a separate tree, audits its reachable Git objects, checks fast-forward ancestry, tests the server against the external Practice Range data, pushes only `main`, and verifies the remote head. Use `--verify-only` to rehearse those checks. Keep the publication filter stable across pushes.
- At handoff, report the project status, branch, latest commit, changelog, test results, client acceptance status, and GitHub sync result.
