Research evidence ledger -- Overwatch 1.74.0.0.104319
Date: 2026-11-05

This ledger records provenance and limits, not independent reproduction of every claim.
The analysis command reads local extracted data. It does not run the client or execute scripts.

A. Target-client structural evidence
  Local game_graphs_174.json.gz, game schemas and graph.py are the structural input.
  tools/extract_game_graphs.py documents extraction from DataTool 01B and body 003 XML.
  The analyzer records the input SHA-256 to make reports reproducible. The bundle has no
  embedded exact-build verification; its target attribution comes from the repository.
  A graph reference closure includes schema references, dormant scripts and conditional
  branches. It is not a list of initialized instances or proven executed gameplay.
  Entry-link candidates follow plug links without evaluating conditions, entry triggers,
  events, time, subgraph invocation or lifecycle. They are not execution reachability.
  A class name, readable parameter or numeric constant alone does not prove its behavior.
  Source indexes, filtered owner/remote slots and presence bits are reported separately.

B. Locally observed behavior (previous session evidence)
  Local login, Practice Range loading, spawn and hero selection were observed; the server
  recorded a hero switch. That does not establish weapons, abilities, damage or full matches.
  This analysis tool adds no new live-client behavior verification.

G. Additional public 1.74 implementation located during this work
  LizRollin/overwatch-1.74-lobby-server, wip, fixed commit:
  9f8f3bcb5eccab6fb7738bee3c2371fcf0623f29
  https://github.com/LizRollin/overwatch-1.74-lobby-server/tree/9f8f3bcb5eccab6fb7738bee3c2371fcf0623f29
  This revision includes script/expr.py, runtime.py, nodes.py, driver.py, decode.py,
  rulesets.py, codec extraction/table data and unit/model tests; it also contains collision,
  movement, combat and projectile implementations. These are new implementation references,
  not proof that the main local project already has those features working in the client.
  Its WIP.md attributes working Soldier combat and training bots to the author's live tests,
  and also lists stuck firing/ammo after kills, Sprint failures, crashes after kills, HUD
  health-number problems, missing ultimate behavior and incomplete match rules. Those are
  upstream claims and known issues, not new independent real-client acceptance here.

  Isolated baseline performed here:
    Export: work/upstream-liz, made by git archive of the fixed commit, with tarfile
    filter='data'; the destination did not previously exist.
    Interpreter: the existing main project's .venv Python, with -B.
    Six inspected suites passed: expression 14, runtime 11, driver 24, codecs 9,
    abilities 11 and game_statescript 6; total 75, no failures/errors/skips.
    Test execution prohibited process launches and socket connect/bind. No blocked
    attempts occurred; no game, server, injection or downloader was started.
    Baseline records: work/liz-validation.json and work/liz-validation.log.
    These results apply to the unmodified fixed-commit export before the separately
    authorized expression robustness patch. The export may change after that baseline.
    Original expr.py SHA-256:
    7940ab23fe9cb8c99858a0e2335f7aacb1f029d865bc6906f711b664b956c580

  A separate robustness investigation reproduced an unbounded expression jump loop with
  expr.run([1, 0]). This case was not covered by the original 75 passing tests. An instruction
  budget and malformed/truncated/jump-target validation were repaired and integrated with
  eight focused regressions in local commit f074003. That commit also integrates the pinned
  upstream implementation and local lifecycle/command repairs. Live-client acceptance remains
  separate and incomplete; see docs/STATE.md.

  Further local tests reproduced event-limit exhaustion that stopped only a weapon instance
  while the driver continued reporting its active volley, cross-instance event cycles that
  exhausted outer loops without an error, and immediate plug recursion. The follow-up repair
  fails the whole component explicitly, clears pending shots/events and prevents later frames.
  It preserves ordered immediate links and queued state begins. No original-server recovery
  behavior is inferred, and these reproductions do not establish the cause of live kill bugs.
  Full follow-up regression: 818 tests, 817 passed, one missing-cache skip. A separate
  62.448-second native-driver/local-decoder sequence completed 3903 owner chunks with no fault.

Acceptance and redirection
  An unsupported node or unknown expression that blocks a scenario remains an explicit
  blocker. Do not count structural node presence or caller-declared handlers as support.
  If the server log agrees but the client rolls back weapon/ammo state, return to body
  initialization, state layout and processed-input acknowledgement before adding damage.
  Prefer independently checked target-client evidence when cross-version sources conflict.
  Preserve unverified parameter meanings and original-server differences in the report.
